# SC4 1.1.641 on network locations: web evidence

Overall: very thin. No source found that tests UNC, SMB, or OneDrive with SC4 directly. Most findings are absence of evidence plus analogy. Simtropolis pages returned HTTP 403 to fetch, so only search snippets were available for them.

**1. `-UserDir:` with UNC or mapped drive.** `-UserDir:"path"` is a documented launch option (quotes needed for spaces; missing subfolders Regions/Plugins/HTTPCache are recreated). All documented examples are local drive paths, e.g. `D:\Data\SC4Profiles\MyProfileName01\` (https://memo33.github.io/sc4pac/ faq, https://github.com/memo33/sc4pac/blob/main/docs/faq.md; https://community.simtropolis.com/omnibus/simcity-4/reference/sc4-command-line-options-r362/ via search snippet). A Simtropolis post (https://community.simtropolis.com/forums/topic/51832-moving-the-location-of-your-simcity-4-folder/, snippet only) says one config file is always read from default Documents but written to the custom dir on exit. No report of UNC or mapped-drive use was found either way. Confidence: high that it exists and works locally; low on network paths (unknown, must be tested).

**2. Regions as junction/symlink to SMB, OneDrive Documents.** No SC4-specific OneDrive breakage report found. Nearest evidence: a Steam thread where iCloud removed local city files and restoring them fixed the region (https://steamcommunity.com/app/24780/discussions/0/3829792183357218414/, snippet), and The Sims 4 threads showing games follow the Windows-designated Documents (OneDrive) path and that sync/placeholder behavior breaks saves (https://forums.ea.com/discussions/the-sims-4-technical-issues-pc-en/re-sims-saving-to-onedrive/11815338). Those are analogy only. SC4 users do use `mklink /D` for the Plugins folder (https://steamcommunity.com/app/24780/discussions/0/3002173313634091455/). Windows junctions cannot target SMB shares; a directory symlink (`mklink /D`) to a UNC path is possible but untested for SC4. Confidence: low.

**3. Two people, one region.** Only asynchronous approaches reported. A Steam guide syncs the whole `Regions\<name>` folder with Syncthing; others see changes after reloading the region view; "Two players cannot work on the same tile at once, and will overwrite each other"; border edits (roads, terrain, trade deals) cause neighbor tile updates that can conflict (https://steamcommunity.com/app/24780/discussions/0/3002173313634091455/). A Dropbox-shared Regions folder is reported to work for two people (Steam thread, 2015, via search snippet), and a CivFanatics thread raises last-saver-overwrites concerns (https://forums.civfanatics.com/threads/simcity4-deluxe-multiplayer-region-play.261043/). SC4MP (https://community.simtropolis.com/forums/topic/762508-introducing-the-simcity-4-multiplayer-project/) is a server/launcher model with separate dirs. A corrupted/modified config.bmp is reported to kick cities to the regional "downloads" folder (Steam, https://steamcommunity.com/app/24780/discussions/0/3829792183357218414/). No report of simultaneous live play on one shared folder, nor of region.ini or .sc4 lock failures. Confidence: medium on the sync-folder reports, low on the rest.

**4. .sc4 open semantics and SMB.** Not covered by any web source found. Repo context (docs/research/save-641.md, Ghidra): own .sc4 is held open GENERIC_READ with FILE_SHARE_READ for the whole session (never FILE_SHARE_DELETE or WRITE); saves go temp file in the region dir (CREATE_NEW share 0), then two `MoveFileA` renames; neighbor .sc4 files are opened write with OPEN_ALWAYS to patch records. Over SMB these share modes are enforced by the server, so a remote writer or renamer of a file another PC holds open would fail the same way (sharing violation, failed rename), and rename-with-open-handle failures would surface as "could not save". Client-side oplock/cache behavior and sync-client placeholders add risk. This is inference from the repo, not a web report. Confidence: medium on semantics, low on SMB specifics.

**5. Null45 and NAM-dll.** GitHub code search over github.com/0xC0000054 found nothing about region sharing. Its sc4-dbpf-loading has UNC handling (`\\?\UNC\` prefix in src/PathUtil.cpp), i.e. long-path support for DBPF file paths, not region sharing. sc4pac documents `-UserDir` for profiles only. Nothing found in NAM-dll (search was not exhaustive). Confidence: medium that no relevant prior art exists.

## Implications for a two-PC design
- Do not rely on a shared SMB Regions folder as the live store; nobody has demonstrated it, and handle-held .sc4 files make failures likely.
- Keep each PC's Regions folder local; sync only the small regional record data (the project's existing file-store seam) over the LAN.
- If a shared folder is still wanted, test `-UserDir:"\\host\share\..."` and `mklink /D` to UNC in a throwaway profile first, watching for sharing violations on the temp-file rename.
- Never let both PCs write the same tile .sc4 or neighbor-patch each other's files; the neighbor OPEN_ALWAYS write across machines is the data-loss window already found in save-641.md.
- Exclude the region dir from OneDrive/Dropbox sync (or move Documents off OneDrive): placeholders and sync locks can break renames.
- Treat region.ini and config.bmp as per-machine or write-once; config.bmp corruption moves cities to downloads.
- Prior art accepts "different tiles per player, reload region view"; the plugin's tile guard matches that model.
- Mind the config-file quirk: some settings read from default Documents but write to the UserDir.
