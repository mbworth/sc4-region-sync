# SMB semantics for the file store (two PCs, one share)

Confidence: H/M/L. Sources marked (fetched) were returned by search this session; others are from knowledge, URLs are the canonical docs but were not re-read.

## Answers

1. **Rename-over-existing atomicity.** MoveFileExW(REPLACE_EXISTING) becomes SMB2 SET_INFO FileRenameInformation (ReplaceIfExists=TRUE) (Win10 uses FileRenameInformationEx/POSIX semantics on NTFS locally; over SMB the client sends the classic form). On a Windows/NTFS server the rename is a single NTFS operation under the directory lock, so a reader on the other host opens either the old or the new file, never a torn one, and never "missing" (H for Windows server, M for Samba, M-L for NAS). Samba does rename(2) on POSIX, which is atomic over an existing target (M-H). Caveats: (a) the rename fails with ACCESS_DENIED / SHARING_VIOLATION if anyone has the destination open without FILE_SHARE_DELETE (a remote reader included; same as local), so retries stay needed; (b) a reader that already had the old file open keeps reading the old inode/data (fine); (c) with the temp file, the writer must have closed it (data flushed to server) before renaming; a client with a write-back cache flushes on close, but call FlushFileBuffers if durability across a server crash matters; (d) the rename is atomic on the server, not necessarily visible instantly to the other client (see 6, 7). Sources: https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/ (SET_INFO, FileRenameInformation); https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw

2. **Change notification.** Works over SMB2/3 via SMB2 CHANGE_NOTIFY; Windows client forwards ReadDirectoryChangesW/FindFirstChangeNotification to it, and changes by other hosts are reported (H for Windows servers, M for Samba, M-L for NAS). Failure modes: (a) buffer overflow returns success with 0 bytes, you must rescan (docs, fetched: https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw); over a network the buffer must be <= 64 KB or the call fails with ERROR_INVALID_PARAMETER (docs, M); (b) NAS vendors document missed notifications and overflows on busy shares (NetApp, fetched: https://kb.netapp.com/on-prem/ontap/Ontap_OS/OS-KBs/Microsoft_.NET_FileSystemWatcher_reports_System.IO.InternalBufferOverflowException); (c) old Samba (3.0.23) failed to deliver them, fixed 3.0.25 (https://bugzilla.redhat.com/show_bug.cgi?id=247447); modern Samba delivers via inotify/kqueue only for changes it sees, so changes made directly on the NAS filesystem (not via smbd) can be missed unless the VFS notify backend watches the underlying fs (M); (d) a dropped session or reconnect loses the pending request; the app must re-arm and rescan (H); (e) SMB1 and DFS/odd NAS modes: often unreliable (L); (f) notification is not ordered with respect to the client's own directory cache: the event may arrive before a listing shows the file (M). Rule: treat it as a wake-up hint only; always back with a poll.

3. **Sharing modes across hosts.** Yes. Share modes are enforced by the server's file system open path, not the client, so host B's open for GENERIC_WRITE against A's FILE_SHARE_READ-only open gets STATUS_SHARING_VIOLATION (ERROR_SHARING_VIOLATION), and FILE_SHARE_DELETE is honored (rename/delete of an open file without it fails, with it succeeds) (H on Windows server, M-H on Samba which emulates with share-mode tables, M on NAS). Exceptions: if the "host" is the same machine as the share and a process opens the file locally, the same rules apply, since the server is the arbiter. Subtlety: Windows client may keep a handle open longer than the app (handle caching via leases): a closed app handle can still hold a server-side open for a short time (up to a few seconds, deferred close with Handle lease), which can make a following rename/delete by another host fail with SHARING_VIOLATION even though the other app closed it (M). Retries are mandatory. Source: https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/ (create/share access), https://learn.microsoft.com/en-us/windows/win32/fileio/creating-and-opening-files

4. **OPEN_ALWAYS vs concurrent rename (save-641 race).** Same as local: CREATE_ALWAYS/OPEN_ALWAYS map to SMB2 CREATE with disposition OPEN_IF, the server evaluates the name lookup atomically against the rename under its own locking. Between the game's two MoveFileA calls, the name does not exist, so OPEN_IF creates an empty file; the race is unchanged, but the window widens by network latency (rename 1 and rename 2 are separate round trips, 1 to several ms on LAN, more on NAS) and by the other client's negative-name caching: the Windows client's FileNotFound cache (default 5 s) can make a reader think a file is missing, and the Windows client may also answer an open from cache. The save lock must therefore span hosts (see 5). H on the logic, M on the widening.

5. **Locks across hosts.**
   - **Named mutex (`Local\...`)**: host-local, useless across PCs. (H)
   - **LockFileEx byte-range locks**: work over SMB2 (SMB2 LOCK request), server-enforced, mandatory for I/O on the locked range (reads/writes by other handles fail with LOCK_CONFLICT), exclusive/shared, with fail-immediately or blocking waits (SMB2 supports async pending locks). Windows server H; Samba M-H (POSIX lock mapping; Samba holds the share mode and POSIX locks; "posix locking" and oplock settings matter); NAS M. Locks are released when the handle closes or the session/connection is torn down by the server.
   - **No-share CreateFile as lock file** (e.g. CREATE_NEW or OPEN_ALWAYS with dwShareMode=0, optionally FILE_FLAG_DELETE_ON_CLOSE): works across hosts via server-side share modes (H Windows, M-H Samba). Preferable to byte-range because the open fails fast with SHARING_VIOLATION, and DELETE_ON_CLOSE cleans up on clean exit and on server-side handle teardown.
   - **Holder crash/disconnect**: the server keeps the open (and its locks / share mode) until it notices the client is gone: TCP reset detection immediate if the client OS is alive and the process dies (handles closed by the client OS, so the lock frees at once); if the whole PC loses power or the network, the server only learns on TCP timeout / SMB keepalive / session idle (Windows server autodisconnect default 15 min idle is for idle sessions; with an outstanding connection, TCP keepalive/retransmit failure typically 20 s to minutes; SMB2 echo/keep alive every ~ 30-60 s on client). Windows SMB3 clients also use durable handles (v1 default ~16 s timeout, v2 and persistent handles up to 60 s, 180 s for CA) and resilient handles (default timeout 120 s in Windows Server when the client asked for it): after a connection drop the server preserves the open and locks for the timeout so the client can reconnect. A crashed client PC therefore leaves the lock held for roughly tens of seconds to minutes (M; source: MS-SMB2 3.3.2.x, durable handle scavenger timer, https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/; https://learn.microsoft.com/en-us/windows-server/storage/file-server/smb-resilient-handles ). Samba: "durable handles" and ping/keepalive are configurable, similar behavior (M). Lease/oplock break: other clients' conflicting opens trigger a lease break to the holder with a 35 s ack timeout on Windows server (MS-SMB2 Oplock Break Acknowledgment Timer, default 35 s; M-H); that only delays data caching, not the lock.
   - **Conclusion**: locks work but are not liveness proof; a held-by-crashed-peer lock can persist ~1 to several minutes. Combine with a lease timestamp in the lock content.

6. **Metadata freshness and clocks.** The Windows SMB2 client caches file attributes (size, mtime) for FileInfoCacheLifetime = 10 s by default, directory contents/enumeration for DirectoryCacheLifetime = 10 s, and "file not found" for FileNotFoundCacheLifetime = 5 s (fetched: https://learn.microsoft.com/en-us/windows-server/administration/performance-tuning/role/file-server ; https://technet.microsoft.com/library/ff686200.aspx). Directory leases (SMB3.0+, on Win8+ server) let the client cache longer and be invalidated by the server on change; when leases are not granted (Samba before 4.x / some NAS / SMB2.0.2) the time-based caches apply. Opening a file (CREATE) always revalidates against the server, so opening and reading data yields fresh content when no lease conflict exists; the stale part is `GetFileAttributes`, `FindFirstFile` and `GetFileAttributesEx` results (up to ~10 s stale) and negative lookups (~5 s). Data caching is coherent via oplocks/leases: a conflicting open by another host breaks the lease and the holder flushes, so reads after the writer closed are consistent (M-H); read caching with Read lease (no handle) can be stale only if the server fails to break (buggy NAS; L). Known client bugs: Win10 1803 directory cache bug, workaround DirectoryCacheLifetime=0 (fetched in search above); Win8 stale cache issue (https://www.mark-gilbert.co.uk/windows-8-smbv2-incorrectly-cached-data-from-a-server-2008-r2-file-share). mtime is stamped by the server (its clock) when the client writes without explicit set, or by the client if the app/redirector sets time explicitly on close (Windows redirector usually lets the server stamp last write on close; copy tools set it explicitly). So comparing mtimes of one file over time is fine as long as only the server (or consistent source) stamps them; do not compare mtimes across hosts. **writtenUnixTime in the snapshot** is stamped by each writer's local clock: skew of seconds (Windows w32time default tolerance is up to minutes on non-domain PCs) will break cross-writer comparisons. Use a monotonic per-writer sequence number plus writer id for ordering, and use time only for staleness hints with a tolerance (e.g. 2 min) or, better, derive "age" from the observer's own clock by noting when it last saw the sequence change. H.

7. **Directory listing freshness.** Yes, host B can miss (or still list the old name of) a file A finished renaming: the client's DirectoryCache (default 10 s) and FileNotFound cache (5 s) apply when no directory lease is held; directory_iterator on Windows uses FindFirstFileEx/NtQueryDirectoryFile (SMB2 QUERY_DIRECTORY), which can be served from cache. With directory leases (SMB3 against a Windows server) the server breaks the lease on change, so freshness is near immediate (M-H); on Samba/NAS you should assume the 10 s window (M). Targeted `CreateFile(path)` opens for a known name are not served from the directory cache for positive hits (revalidated by CREATE), but negative lookups can be cached for 5 s. Mitigation: poll by opening known filenames, tolerate 10+ s latency, or set DirectoryCacheLifetime=0 and FileInfoCacheLifetime=0, FileNotFoundCacheLifetime=0 on both PCs via Set-SmbClientConfiguration (admin; documented: https://learn.microsoft.com/en-us/previous-versions/windows/desktop/smb/setconfiguration-msft-smbclientconfiguration) at some cost in chatter.

## Rules for the store on SMB

- Rely on: server-side atomic rename-over-existing (readers see old or new, never torn), with retry for SHARING_VIOLATION on the writer and a tolerant reader (retry open, treat parse failure as "try again next poll").
- Rely on: server-enforced share modes and FILE_SHARE_DELETE semantics; but expect lingering server-side handles for seconds after close, so retry loops should span ~ 1 to 5 s, not 100 ms.
- Never rely on: `Local\` named mutexes, in-process state, or directory listing for correctness across hosts; replace the save lock with a cross-host file lock (CreateFile share=0 lock file, or LockFileEx on a lock file), wrapped around the same save region.
- Never rely on: change notification alone; it is a wake-up hint. Always keep a periodic poll (every 1 to 2 s) and rescan on overflow, reconnect, or ERROR_INVALID_PARAMETER (64 KB limit; use a 16 KB buffer).
- Never rely on: directory listing or GetFileAttributes freshness within 10 s; detect new snapshots by opening the known `<x>_<z>.snapshot` names and comparing an in-file sequence number, not by mtime or listing.
- Never rely on: negative lookups (missing file) being current for 5 s; a missing file means "not yet", not "peer gone".
- Never compare timestamps across hosts. Order by (writerId, monotonic sequence). Use `writtenUnixTime` only for display or coarse staleness (> 2 min), and judge liveness by "sequence did not advance in my local clock's T seconds".
- Needs heartbeat or lease: the save lock and writer liveness. A lock held by a crashed PC (power loss, network drop) can persist 20 s to several minutes (durable/resilient handle timeouts). Write a lease record (holder id, local monotonic expiry, renewed every few seconds) into the lock file; peers may treat an expired lease as breakable after a grace greater than the clock skew and handle timeout, logged loudly.
- Keep the temp file in the same directory as the target (same share, same volume) and close it before rename; ensure lock and snapshot files are on one server, never DFS-replicated or synced (OneDrive/Syncthing) folders.
- Prefer hosting the share on a Windows PC (or a recent Samba with SMB3, directory leases and strict locking on) over a consumer NAS; test the NAS with a small harness (rename loop on host A, open/read loop and ReadDirectoryChangesW on host B, count torn reads, missed events, listing lag) before committing.
